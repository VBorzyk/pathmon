**CLI-утилита, которая измеряет доступность сервиса из сети клиента и отличает отказ сетевого пути от отказа самого сервиса.**

> ⚠️ **Ранняя стадия.** Работают непрерывное наблюдение по TCP, классификация ошибок, детект четырёх событий, алерты в Telegram и журнал событий.
> Актуальное состояние — в разделе [Статус](#статус).

---

## Проблема

Сервис работает. Health-check зелёный, нагрузка в пределах нормы, метрики хоста чистые. При этом часть пользователей подключиться не может.

Классический мониторинг такую ситуацию не видит по построению. Он отвечает на вопрос «жив ли сервер» и наблюдает либо изнутри самого хоста (Zabbix, node_exporter), либо снаружи из дата-центров сервиса мониторинга (uptime-чекеры). Обе точки находятся не там, где произошёл отказ: он на сетевом пути между пользователем и сервисом — у оператора связи, на транзитном участке, на оборудовании фильтрации трафика.

Разрыв между «сервис жив» и «сервис доступен» оплачивается напрямую: SLA считается по доступности для клиента, а не по аптайму процесса. Пока источником правды остаётся мониторинг из ЦОД, инцидент обнаруживается по обращениям в поддержку — то есть спустя часы после начала деградации.

Типовые сценарии:

- фильтрация, приоритизация или разрыв соединений на оборудовании оператора связи;
- деградация транзитного участка у одного провайдера при исправном пути у остальных;
- смена BGP-маршрута с уходом трафика на перегруженный аплинк;
- недоступность внешнего API или партнёрского сервиса, наблюдаемая только из части регионов.

Pathmon переносит точку наблюдения: агент ставится в ту же сеть, где находятся пользователи, и измеряет доступность оттуда.

**Для кого это сейчас.** Первые пользователи — владельцы частных серверов за рубежом и небольшие операторы с парком из нескольких VPS: выделенные IP, клиенты ходят на серверы напрямую. Формулировка проблемы шире этого сценария, но инструмент растёт из него — под него расставлен и порядок в [Roadmap](#roadmap).

**Несущий сигнал — TCP-подключение, а не ICMP.** Оборудование фильтрации работает на уровне TCP/TLS: дропает SYN, инжектит RST, фингерпринтит протокол. ICMP при этом не трогается, поэтому `ping` и `traceroute` во время инцидента проходят идеально и подтверждают, что всё в порядке.

| Что видим | Диагноз |
|---|---|
| Connect ok, время установления в норме | сервис доступен |
| SYN уходит, ответа нет | **блэкхол** — трафик отбрасывается на пути |
| RST приходит быстрее, чем RTT до хоста | **инжект RST** — соединение рвёт промежуточное устройство |
| Connect ok, но время установления выросло | деградация канала, не блокировка |
| Наблюдатель потерял хост, сам хост видит сеть нормально | отказ на пути, а не отказ сервиса |

Деградация обычно идёт лесенкой: сначала растут потери и время подключения у одного оператора, потом RST на части соединений, потом полный блэкхол. Между первым и последним — часто часы. Это и есть окно для реакции, ради которого утилита существует.

## Схема наблюдения

**Наблюдать нужно из той сети, где сидят пользователи.** Проба, запущенная с самой площадки сервиса, отказ на пути не увидит: маршрут наружу остаётся прежним.

```
   сеть пользователей                           площадка сервиса
┌──────────────────────┐                    ┌──────────────────────┐
│  наблюдатель         │──── пробы ────────>│  сервис              │
│  (VPS у оператора)   │     tcp/443        │  · pathmon watch     │
│  · pathmon watch     │                    │  · пробы до якорей   │
└──────────┬───────────┘                    └──────────┬───────────┘
           │                                           │
           └───────────>  Telegram-чат  <──────────────┘
                   (тег host_id в каждом алерте)
```

Одна и та же бинарка, разные конфиги. Центрального сервера нет — общий чат его заменяет. Это осознанное решение: для пяти хостов контроллер с базой добавляет точку отказа и ничего не даёт сверх того, что даёт общий чат.

**Частный случай, ради которого утилита писалась.** Сервис размещён за пределами РФ, пользователи внутри РФ, фильтрацию выполняет ТСПУ на стороне оператора. Наблюдателя в этом случае ставят внутри РФ — на дешёвый VPS у местного провайдера или на мини-ПК в офисе.

## Установка

```bash
git clone https://github.com/VBorzyk/pathmon.git
cd pathmon
make build          # ./bin/pathmon
```

Скопируйте пример конфига и укажите свои цели:

```bash
cp pathmon.example.yaml pathmon.yaml
./bin/pathmon watch
```

```
$ ./bin/pathmon watch -c pathmon.yaml
pathmon dev | host_id=ru-obs | targets=2 | interval=60s | journal=pathmon.jsonl | telegram=off

14:22:01  my-vpn.example.com:443   ok       streak=0   loss=0/1   18.412ms
14:22:01  1.1.1.1:443              ok       streak=0   loss=0/1   12.031ms
14:23:01  my-vpn.example.com:443   timeout  streak=1   loss=1/2   dial tcp 203.0.113.7:443: i/o timeout
14:23:01  1.1.1.1:443              ok       streak=0   loss=0/2   12.4ms
```

Колонка статуса — результат классификации ошибки: `ok`, `timeout` (истекло время ожидания; распознанные DNS-ошибки исключены), `refused` (отказ в подключении), `error` (DNS, `no route` и прочие ошибки). `streak` — сколько проб подряд провалилось, `loss` — сколько из последних 10 проб провалилось. Детект строится на этих числах, а не на тексте ошибок.

**DNS-ошибки, включая таймаут разрешения имени, получают статус `error`.** Они учитываются в общей серии неудач и в `loss`, но не накапливают серию TCP-таймаутов для `blackhole`. Для цели, заданной именем, замер `TCPConnect` по-прежнему включает и DNS, и подключение: отдельного измерения времени DNS пока нет.

Когда детектор находит проблему, под строкой пробы появляется строка события:

```
14:31:07  my-vpn.example.com:443   timeout  streak=5   loss=5/10  dial tcp 203.0.113.7:443: i/o timeout
14:31:07  my-vpn.example.com:443   !! blackhole: 5 timeouts in a row: SYNs leave, nothing answers
```

События: `blackhole` (серия таймаутов — трафик отбрасывается на пути), `rst_injected` (RST пришёл быстрее половины медианного времени подключения — ответил не хост, а устройство по пути), `slow_connect` (время подключения выросло относительно медианы), `recovered`. Активное событие сообщается один раз, а не каждым обходом; правила по времени молчат, пока в окне нет 5 успешных проб — без базовой линии медиана бессмысленна.

Первый обход выполняется сразу, дальше — раз в `interval`. Расписание фиксированное: время самих проб не накапливается в сдвиг.

| Флаг | Назначение | По умолчанию |
|---|---|---|
| `-c`, `-config` | путь к конфигу | `pathmon.yaml` |
| `-interval` | переопределить интервал из конфига | из файла |
| `-once` | один обход и выход — ручная проверка целей | `false` |
| `-no-notify` | события печатать, в Telegram не слать | `false` |

`-once` выполняет только один обход: история между запусками не сохраняется, поэтому этот режим не заменяет непрерывный детект. Неудачная проба сама по себе не меняет код завершения команды на ненулевой. Для постоянного мониторинга используйте `watch`, в том числе под управлением systemd.

`-no-notify` — режим настройки: сутки гоняете на реальном хосте и смотрите по журналу, сколько алертов прилетело бы и какие из них ложные.

### Запуск через systemd

В `deploy/systemd/` находятся unit-файл и пример окружения. Они предназначены для Linux с systemd 235 или новее, независимо от дистрибутива. В WSL управление сервисом доступно, если systemd включён; сборку и Go-тесты можно выполнять и без него.

Unit запускает существующий непрерывный `watch`: интервал проб задаётся конфигом Pathmon. systemd управляет запуском, остановкой и перезапуском процесса.

Команды ниже выполняются из корня репозитория на целевом Linux. Сначала проверьте код и соберите бинарку для этой машины:

```bash
go test ./...
go vet ./...
make build
```

**Первая установка.** Создайте отдельного системного пользователя без возможности входа и установите файлы. Если пользователь `pathmon` уже создан для этого сервиса, повторять `useradd` не нужно. Команда копирования конфига ниже предназначена для первой установки: существующий рабочий конфиг при обновлении сохраняйте.

<details>
<summary>Описание установки</summary>

```bash
sudo useradd --system --user-group --home-dir /var/lib/pathmon --no-create-home --shell /bin/false pathmon
sudo install -o root -g root -m 0755 bin/pathmon /usr/local/bin/pathmon
sudo install -d -o root -g pathmon -m 0750 /etc/pathmon
sudo install -o root -g pathmon -m 0640 pathmon.example.yaml /etc/pathmon/pathmon.yaml
sudo install -o root -g root -m 0644 deploy/systemd/pathmon.service /etc/systemd/system/pathmon.service
sudoedit /etc/pathmon/pathmon.yaml
```

В установленном конфиге замените пример цели на свой адрес, задайте уникальный `host_id` (или удалите поле, чтобы использовать hostname). Для журнала укажите абсолютный путь:

```yaml
journal:
  path: /var/lib/pathmon/events.jsonl
```

Каталог `/var/lib/pathmon` создаст systemd при запуске, с владельцем `pathmon`. Unit разрешает сервису запись в этот каталог; `/etc` и `/usr` доступны ему только для чтения, домашние каталоги скрыты. Если нужен другой путь журнала, права и ограничения unit необходимо настроить отдельно.

**Telegram — по необходимости.** Если `telegram.chat_id` не задан, файл окружения не требуется. Если задан, установите пример окружения и впишите токен в установленный файл:

```bash
sudo install -o root -g root -m 0600 deploy/systemd/pathmon.env.example /etc/pathmon/pathmon.env
sudoedit /etc/pathmon/pathmon.env
```

Раскомментируйте `PATHMON_TELEGRAM_TOKEN` и замените заглушку. Формат — `KEY=value`, без `export`. systemd читает файл от root, затем передаёт окружение процессу сервиса. Переменные, экспортированные в вашей интерактивной оболочке, автоматически в этот сервис не попадут. Пример также содержит настройки прокси для Telegram.

**Проверка и запуск:**

```bash
sudo systemd-analyze verify /etc/systemd/system/pathmon.service
sudo systemctl daemon-reload
sudo systemctl enable --now pathmon.service
systemctl status pathmon.service --no-pager
sudo journalctl -u pathmon.service -n 50 --no-pager
```

Ожидаемый результат — `active (running)` и строки проб в журнале. `network-online.target` задаёт порядок старта, но не гарантирует доступность целей или DNS. Ошибки проб не завершают `watch`: программа продолжает наблюдение. Если сам процесс завершится с ошибкой, `Restart=on-failure` назначит повторный запуск через 5 секунд; стандартные ограничения частоты стартов systemd остаются в силе. После исправления ошибки запуска при необходимости выполните `sudo systemctl reset-failed pathmon.service` и запустите сервис снова.

**Два разных журнала:** `journalctl` показывает stdout/stderr — строки проб и ошибки. NDJSON-файл хранит события детектора для команды `history`:

```bash
sudo -u pathmon /usr/local/bin/pathmon history -config /etc/pathmon/pathmon.yaml -since 24h
```

При здоровых целях файл событий может быть пустым. Проверьте также остановку и повторный запуск:

```bash
sudo systemctl stop pathmon.service
systemctl is-active pathmon.service
sudo systemctl start pathmon.service
systemctl is-active pathmon.service
```

После остановки ожидается `inactive` (и ненулевой код `is-active`), после запуска — `active`. Ручная остановка не вызывает автоматический перезапуск.

Остановка сейчас использует обычный SIGTERM: приложение ещё не реализует управляемое завершение через `context`. История проб, активные инциденты и очередь Telegram находятся в памяти и сбрасываются при рестарте; NDJSON-файл сохраняется. Unit не меняет эти свойства программы.

**Обновление бинарки:** после проверок и `make build` остановите сервис, замените исполняемый файл и запустите его снова. Конфиг и файл окружения повторно копировать не нужно.

```bash
sudo systemctl stop pathmon.service
sudo install -o root -g root -m 0755 bin/pathmon /usr/local/bin/pathmon
sudo systemctl start pathmon.service
```

После изменения YAML или файла окружения выполните `sudo systemctl restart pathmon.service`. После изменения unit сначала скопируйте его в `/etc/systemd/system/`, выполните `sudo systemctl daemon-reload`, затем перезапустите сервис.

</details>

### Журнал и `history`

Каждое событие пишется в файл `journal.path` — по одной JSON-строке, без cooldown и без группировки. Чат показывает то, что нужно прочитать; журнал хранит всё. Фильтрация нестабильна во времени — окна, когда всё работает, и региональные волны видны только по истории.

```
$ pathmon history -since 24h
2026-09-04 12:10:11  ru-obs         my-vpn.example.com:443   blackhole    5 timeouts in a row: SYNs leave, nothing answers
2026-09-04 12:31:11  ru-obs         my-vpn.example.com:443   recovered    connect ok again
```

| Флаг `history` | Назначение |
|---|---|
| `-c`, `-config` | конфиг, из которого берётся `journal.path` |
| `-target host:port` | только эта цель |
| `-since 24h` | только события новее |
| `-n 20` | последние N подходящих |

Файл — обычный NDJSON, `--json` у `history` не нужен: `jq` читает его напрямую.

```bash
jq -c 'select(.event == "blackhole")' pathmon.jsonl
```

Время в файле — UTC, `host_id` — в каждой строке: журналы с нескольких наблюдателей склеиваются `cat`-ом без пересчёта зон. `history` показывает локальное время — то же, что в выводе `watch`. Строка пишется одним вызовом `write` без буфера: прерванный процесс не оставляет обрезанной записи, а если она всё же появится (сбой питания), `history` пропустит её с предупреждением, а не откажется читать файл.

## Конфигурация

```yaml
# pathmon.yaml
host_id: ru-observer-1        # тег в алертах; по умолчанию — hostname
interval: 60s
timeout: 2s                   # должен быть короче интервала

targets:
  - host: my-vpn.example.com
    port: 443
  - host: 1.1.1.1             # якорь: контрольная цель
    port: 443

telegram:                     # секция необязательна: без chat_id алерты только в stdout
  chat_id: 123456789
  # api_base: https://api.telegram.org   # эндпоинт Bot API; см. ниже
  # cooldown: 15m

journal:
  path: pathmon.jsonl         # журнал событий; без path — выключен
```

**Токен бота задаётся только через `PATHMON_TELEGRAM_TOKEN`.** В конфиг и во флаги он не принимается: значение флага видно в `/proc/*/cmdline` любому пользователю хоста, в `ps` и в `docker inspect`. Если `chat_id` задан, а переменной нет, `watch` не стартует — молчащий алертинг хуже отсутствующего.

`chat_id` — число, не username. Бот не может написать первым: сначала отправьте ему любое сообщение (или добавьте в группу), затем найдите `"chat":{"id":...}` в ответе `https://api.telegram.org/bot<TOKEN>/getUpdates`. У групп id отрицательный.

Одно сообщение на обход — все события круга одним текстом:

```
pathmon @ ru-observer-1
15:02:44  blackhole  my-vpn.example.com:443
  5 timeouts in a row: SYNs leave, nothing answers
```

<details>
<summary>Доставка алертов из сети с фильтрацией: api_base, прокси, повтор неотправленного</summary>

Алерт идёт по той же сети, за которой Pathmon наблюдает. Отсюда три правила.

**`api_base`.** Если `api.telegram.org` из сети наблюдателя недоступен, укажите адрес реверс-прокси на хосте за её пределами — достаточно nginx с одним `proxy_pass https://api.telegram.org`. Тот же параметр принимает адрес самостоятельного Bot API Server.

**Прокси.** Отдельного поля нет: стандартный HTTP-клиент Go читает `HTTPS_PROXY` / `NO_PROXY` из окружения, поддерживаются `http://` и `socks5://`. Прокси действует только на доставку в Telegram — TCP-пробы идут напрямую, иначе измерялся бы путь до прокси, а не до цели.

**Прокси не должен стоять на наблюдаемой цели.** Если алерт о недоступности хоста X идёт через X, блэкхол X съест и сам алерт. Реле — на хосте у другого провайдера.

Если Telegram недоступен, обход печатает ошибку в stderr и продолжает пробы; неотправленный текст уходит следующим обходом вместе с новыми событиями. Хранится до 20 неотправленных — полный след даст журнал.

</details>

## Как устроен детект

Реализовано в `internal/detect` и покрыто табличными тестами; потери с гистерезисом — в плане.

**Блэкхол.** Серия из 5 результатов `timeout` подряд. Распознанные DNS-ошибки, включая DNS-таймауты, классифицируются как `error` и прерывают эту серию. Пять отказов `refused` тоже не дают `blackhole`. Серия таймаутов — признак недоступности, а не доказательство места или причины отказа. Якорные цели помогают при чтении алертов: одновременные проблемы у нескольких целей дают повод проверить наблюдателя и общий участок пути; автоматической корреляции между целями пока нет.

**Инжект RST.** RST — легальный ответ на закрытый порт. Признак вмешательства — RST, пришедший быстрее **половины медианного** времени установления соединения с этим хостом: значит ответил не хост, а промежуточное устройство. Для этого проба замеряет время и на пути ошибки, а не только при успехе.

**Время подключения.** Медиана + MAD по скользящему окну, а не среднее: одиночный выброс не должен сдвигать норму. Масштаб с полом `max(1.4826·MAD, median/4, 1ms)` — на стабильном канале MAD обращается в ноль, и без пола любое дрожание становится «бесконечным отклонением». Пол откалиброван суточным прогоном: `median/10` на стабильных якорях ловил обычное дрожание сети. Базовая линия строится по окну **без** оцениваемой пробы: точка не должна влиять на норму, по которой её судят.

**Один инцидент — одно событие.** Активная проблема не повторяется каждым обходом; закрывает её `recovered`. Выздоровление от `slow_connect` требует возврата времени к норме, а не просто успешной пробы — иначе затяжная деградация дребезжит парой `slow_connect`/`recovered` на каждом обходе. Правила по времени молчат, пока в окне нет 5 успешных проб: без базовой линии медиана бессмысленна.

**Потери** *(в плане)*. Скользящее окно с гистерезисом: вход в аномалию при 5%, выход при 2%. Без разных порогов алерт дребезжит на границе.

**Cooldown.** Повторные события того же типа по той же цели подавляются на 15 минут (`telegram.cooldown`). Исключение — `recovered`: оно уходит всегда, иначе алерт остаётся без закрывающей строки. Cooldown живёт в слое доставки (`internal/notify`), а не в детекторе: журнал получает всё, чат — без повторов. Журнал — это третья реализация того же интерфейса `Notifier`, просто без фильтрации.

## Осознанные решения по скоупу

- **Нет центрального сервера, базы и веб-UI.** Одна бинарка, состояние в памяти, журнал в файл. Для десятка хостов этого достаточно.
- **Трассировка вынесена во второй этап.** Она даёт контекст («маршрут сменился»), но не даёт основной сигнал: отказ на пути виден по TCP, а не по ICMP. Сначала — то, что работает.
- **IPv4 только.**
- **Состояние не переживает рестарт.** После перезапуска базовая линия отстраивается заново, в это время алертов не будет.
- **Диагнозы — гипотезы, а не факты.** `BLACKHOLE` означает «картина типична для блокировки», не «вас точно заблокировали».

## Что Pathmon не видит

Каждое — следствие того, что проба заканчивается на установлении соединения.

| Слепое пятно | Почему проба говорит `ok` | Чем закрывается |
|---|---|---|
| Соединение установилось, но данные не идут: поток замораживается после первых десятков КБ или полоса душится до нуля | TCP-handshake проходит целиком — вмешательство начинается позже | проба с нагрузкой (Roadmap) |
| Подмена ответа DNS у оператора | заглушка принимает соединение на 443 — «доступность» подтверждает не тот сервер; косвенный след: время подключения резко *улучшилось* | сверка резолвинга через DoH (Roadmap) |
| Разрыв по имени хоста (SNI) для целей за общим IP | RST приходит после ClientHello, а TCP-проба завершается до него | TLS-проба с контрольным SNI (Roadmap) |
| Поведенческая фильтрация: решение по числу параллельных соединений, длительности сессий, профилю трафика | одиночная короткая проба не похожа на трафик, по которому принимается решение | пробой не закрывается в принципе |

Последняя строка — граница инструмента: такое видно только по реальным сессиям.

## Чем отличается от существующего

| Инструмент | Чем не подходит |
|---|---|
| `mtr`, `trippy` | Интерактивные, без истории и алертов |
| SmokePing | Графики RTT, но не различает причины недоступности |
| `blackbox_exporter` | Умеет TCP-пробу, но не даёт диагноз и требует Prometheus |
| Uptime-чекеры | Наблюдают из своих ЦОД: отказ на пути от сети пользователя не видят в принципе |

Ниша Pathmon — не «ещё один пингер», а проба из точки, где находятся ваши пользователи, с ответом на вопрос *почему* недоступно.

## Стек

| Слой | Технология |
|---|---|
| Язык | Go 1.24+ |
| CLI | stdlib, диспетчер команд на `switch` |
| TCP-пробы | stdlib `net` |
| Конфиг | `gopkg.in/yaml.v3` |
| Планировщик | stdlib `time`, расписание от фиксированной точки |
| Telegram | stdlib `net/http`, Bot API напрямую |
| Журнал | NDJSON, stdlib `encoding/json`, `bufio` |
| Трассировка | `golang.org/x/net/icmp` *(этап 2)* |
| Сборка | Makefile + `-ldflags`, кросс-компиляция |

Зависимости добавляются только когда без них не обойтись. Для утилиты, которую ставят на чужие production-хосты, каждая транзитивная зависимость — это чужой код с сетевым доступом.

<details>
<summary>Почему не CLI-фреймворк, не viper и не библиотека для Telegram</summary>

- **CLI-фреймворк** (cobra, urfave/cli, kong). Три команды. Диспетчер на `switch` — 20 строк, читаются без документации. Вернуться к фреймворку имеет смысл, когда команд станет больше десяти.
- **viper.** Слияние «флаг > env > yaml > дефолт» для дюжины полей — это явные 40 строк. viper приносит 30+ транзитивных зависимостей и неявные правила приоритета.
- **Telegram-библиотека.** Нужен ровно один метод — `sendMessage`. Это один `http.Post`. Библиотеки тянут поллинг апдейтов, вебхуки и типы для всего Bot API.

</details>

```
├── pathmon.example.yaml
├── Makefile
└── go.mod
```

## Roadmap

Порядок — по ценности для основного сценария, не по сложности.

- [x] Конфиг, TCP-проба, цикл наблюдения
- [x] Детект: серия таймаутов, ранний RST, рост времени подключения
- [x] Алерты в Telegram с cooldown
- [x] Журнал событий (NDJSON) и команда `history`
- [x] Unit-файл и инструкция запуска через systemd
- [ ] **ICMP-трассировка и детект смены маршрута.** Отвечает «где» и служит контролем для остальных проб: путь цел, а данные не идут — фильтрация; путь сменился — сетевая авария
- [ ] **Проба с нагрузкой: TLS-handshake + скачивание, событие `stalled`.** Фиксирует, на каком объёме и после какой скорости встал поток: обрыв на характерном объёме — почерк фильтра, равномерно низкая скорость — деградация канала. Отдельный редкий интервал: проба стоит трафика
- [ ] **UDP-якорь: DNS-запрос или QUIC до публичного резолвера** — пропускает ли эта сеть UDP вообще. Проба до собственной цели не делается: современные протоколы молчат на неаутентифицированные пакеты, «нет ответа» ничего не различает
- [ ] **Сверка резолвинга через DoH.** Включается автоматически для целей, заданных именем; для IP не нужна
- [ ] **TLS ClientHello с контрольным SNI на тот же IP.** Только для целей за общим IP (CDN, облако), где режут по имени; для выделенных IP бесполезна
- [ ] Персистентное состояние между рестартами, Prometheus `/metrics`, IPv6
