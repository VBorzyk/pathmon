## Проблема

Ваш VPN-сервер во Франкфурте жив, пингуется, нагрузка в норме. А пользователи из Ростелекома подключиться не могут.

Обычный мониторинг этого не увидит: uptime-чекеры смотрят на сервер снаружи из своих ЦОД, а Zabbix — изнутри самого сервера. Проблема же на пути, у российского провайдера.

Ключевая деталь: **ТСПУ не режет ICMP.** Блокировка работает по TCP/TLS — дропает SYN, инжектит RST, фингерпринтит протокол. Поэтому `ping` и `traceroute` в момент блокировки проходят идеально и рапортуют, что всё хорошо.

Pathmon смотрит на TCP-подключение и различает состояния:

| Что видим | Диагноз |
|---|---|
| Connect ok, время установления в норме | всё живо |
| SYN уходит, ответа нет | **блэкхол** — типовой почерк блокировки |
| RST прилетает быстрее, чем RTT до хоста | **инжект RST** по пути |
| Connect ok, но время установления выросло | деградация сети, не блокировка |
| Наблюдатель в РФ потерял хост, сам хост видит сеть нормально | блокировка, а не падение |

Деградация обычно идёт лесенкой: сначала растут потери и время подключения у одного оператора, потом RST на части соединений, потом полный блэкхол. Между первым и последним — часто часы. Это и есть окно, ради которого утилита существует.

## Схема наблюдения

**Наблюдать нужно изнутри РФ.** С VPS во Франкфурте блокировку не видно: путь наружу остаётся прежним.

```
        РФ                                    зарубеж
┌──────────────────┐                    ┌──────────────────┐
│  наблюдатель     │───── пробы ───────▶│  VPN-сервер      │
│  (дешёвый VPS    │      tcp/443       │  ・ pathmon watch │
│   или мини-ПК)   │                    │  ・ пробит якоря  │
│  ・ pathmon watch │                    └────────┬─────────┘
└────────┬─────────┘                             │
         │                                       │
         └──────────▶  Telegram-чат  ◀───────────┘
                    (тег host_id в каждом алерте)
```

Одна и та же бинарка, разные конфиги. Центрального сервера нет — общий чат его заменяет. Это осознанное решение: для пяти хостов контроллер с базой добавляет точку отказа и ничего не даёт сверх того, что даёт общий чат.

## Статус

Разработка идёт этапами: сначала TCP-пробы (несущий сигнал для детекта блокировок), трассировка — после.

**Этап 1 — TCP-мониторинг**

| Возможность | Статус |
|---|---|
| Каркас CLI, сборка, CI | ✅ готово |
| Чтение конфига из YAML | 🚧 в работе |
| TCP-проба: успех / таймаут / RST | 📋 запланировано |
| Цикл наблюдения с интервалом | 📋 запланировано |
| Детект: серия отказов, рост времени подключения | 📋 запланировано |
| Алерты в Telegram с cooldown | 📋 запланировано |
| Журнал событий (NDJSON) | 📋 запланировано |

**Этап 2 — трассировка маршрута.** ICMP-трассировка, детект смены пути, аномалии RTT по медиане/MAD.

**Этап 3 — параллельные пробы, UDP-канарейка** для отличия фингерпринтинга WireGuard от падения хоста.

## Установка

```bash
git clone https://github.com/VBorzyk/pathmon.git
cd pathmon
make build          # ./bin/pathmon
```

Сейчас работают только служебные команды:

```
$ ./bin/pathmon version
pathmon dev

```

## Планируемый интерфейс

Так это будет выглядеть по завершении этапа 1:

```yaml
# pathmon.yaml
host_id: ru-observer-1        # тег в алертах; по умолчанию — hostname
interval: 60s

targets:
  - host: my-vpn.example.com
    port: 443
  - host: 1.1.1.1             # якорь: контрольная цель
    port: 443

telegram:
  chat_id: 123456789
```

```
$ pathmon watch
14:22:01  ru-obs  my-vpn.example.com:443  OK          connect 18ms
14:31:12  ru-obs  my-vpn.example.com:443  SLOW        connect 18ms → 340ms
15:02:44  ru-obs  my-vpn.example.com:443  BLACKHOLE   SYN без ответа ×5
```

**Токен бота будет задаваться только через `PATHMON_TELEGRAM_TOKEN`.** В конфиг и во флаги он не принимается: значение флага видно в `/proc/*/cmdline` любому пользователю хоста, в `ps` и в `docker inspect`.

## Как будет устроен детект

Раздел описывает проектные решения, реализация — по мере продвижения этапа 1.

**Блэкхол.** Не «один таймаут — алерт». Подтверждение сериями: N неудачных подключений подряд при том, что другие цели с этого же наблюдателя отвечают. Иначе каждое моргание Wi-Fi станет «блокировкой».

**Инжект RST.** RST — легальный ответ на закрытый порт. Признак вмешательства — RST, пришедший **быстрее**, чем типичное время установления соединения с этим хостом: значит ответил не хост, а промежуточное устройство.

**Время подключения.** Медиана + MAD по скользящему окну, а не среднее: одиночный выброс не должен сдвигать норму. Масштаб с полом `max(1.4826·MAD, 0.1·median, 1ms)` — иначе на стабильном канале MAD обращается в ноль и любое дрожание становится «бесконечным отклонением». Точки, помеченные аномальными, в базовую линию не попадают, чтобы затяжная деградация не «переползла» в новую норму.

**Потери.** Скользящее окно с гистерезисом: вход в аномалию при 5%, выход при 2%. Без разных порогов алерт дребезжит на границе.

**Cooldown.** Повторные события того же типа по той же цели подавляются на 15 минут.

## Осознанные решения по скоупу

- **Нет центрального сервера, базы и веб-UI.** Одна бинарка, состояние в памяти, журнал в файл. Для десятка хостов этого достаточно.
- **Трассировка вынесена во второй этап.** Она даёт контекст («маршрут сменился»), но не даёт основной сигнал: блокировку видно по TCP, а не по ICMP. Сначала — то, что работает.
- **IPv4 только.**
- **Состояние не переживает рестарт.** После перезапуска базовая линия отстраивается заново, в это время алертов не будет.
- **Диагнозы — гипотезы, а не факты.** `BLACKHOLE` означает «картина типична для блокировки», не «вас точно заблокировали».

## Чем отличается от существующего

| Инструмент | Чем не подходит |
|---|---|
| `mtr`, `trippy` | Интерактивные, без истории и алертов |
| SmokePing | Графики RTT, но не различает причины недоступности |
| `blackbox_exporter` | Умеет TCP-пробу, но не даёт диагноз и требует Prometheus |
| Uptime-чекеры | Смотрят снаружи из своих ЦОД, российскую блокировку не видят в принципе |

Ниша Pathmon — не «ещё один пингер», а проба из точки, где находятся ваши пользователи, с ответом на вопрос *почему* недоступно.

## Стек

| Слой | Технология |
|---|---|
| Язык | Go 1.24+ |
| CLI | stdlib, диспетчер команд на `switch` |
| TCP-пробы | stdlib `net` |
| Конфиг | `gopkg.in/yaml.v3` *(этап 1)* |
| Telegram | stdlib `net/http`, Bot API напрямую *(этап 1)* |
| Журнал | NDJSON, stdlib `encoding/json` *(этап 1)* |
| Трассировка | `golang.org/x/net/icmp` *(этап 2)* |
| Сборка | Makefile + `-ldflags`, кросс-компиляция |

Зависимости добавляются только когда без них не обойтись. Для утилиты, которую ставят на чужие production-хосты, каждая транзитивная зависимость — это чужой код с сетевым доступом.

<details>
<summary>Почему не CLI-фреймворк, не viper и не библиотека для Telegram</summary>

- **CLI-фреймворк** (cobra, urfave/cli, kong). Три команды. Диспетчер на `switch` — 20 строк, читаются без документации. Вернуться к фреймворку имеет смысл, когда команд станет больше десяти.
- **viper.** Слияние «флаг > env > yaml > дефолт» для дюжины полей — это явные 40 строк. viper приносит 30+ транзитивных зависимостей и неявные правила приоритета.
- **Telegram-библиотека.** Нужен ровно один метод — `sendMessage`. Это один `http.Post`. Библиотеки тянут поллинг апдейтов, вебхуки и типы для всего Bot API.

</details>

## Разработка

```bash
make build       # сборка в ./bin
make test        # go test ./...
make fmt         # go fmt ./...
```

```
pathmon/
├── cmd/pathmon/        # точка входа, диспетчер команд
├── .github/workflows/  # CI: gofmt, vet, test, build
├── Makefile
└── go.mod
```

Пакеты в `internal/` добавляются по мере реализации. Каталог `internal/` — не соглашение, а правило, которое проверяет компилятор: такие пакеты нельзя импортировать из чужого модуля.
